# Level 3 – Day 3 Content Document

## Create the Value

### Idea Generation and Simple Value Proposition

**Programme:** DECI Summer Camp
**Level:** Level 3 Students
**Day Duration:** 3 hours, including two 15-minute breaks
**Delivery Language:** English
**Learning Approach:** Game-based, collaborative, and idea-driven
**Daily Output:** Project Idea Card + Simple Value Proposition

---

# 1. Day Overview

Day 3 moves teams from understanding the user to developing possible solutions.

Students begin by generating a wide range of ideas without immediately judging or rejecting them. They then use technical perspectives and clear decision-making criteria to improve, compare, and select their strongest option.

By the end of the day, each team will have selected one project idea, explained the value it creates for the identified user, and identified the main assumption that needs to be tested through a prototype on Day 4.

### Essential Question

**How can we create an idea that is useful and worth choosing?**

### Day Purpose

Students learn that a strong project idea is not simply creative or technically impressive. It should:

* Respond to a real user need.
* Create a clear and meaningful benefit.
* Be realistic enough to explore with the available time and materials.
* Be possible to test through a simple prototype.

---

# 2. Learning Objectives

By the end of the day, students will be able to:

1. Generate several possible solutions for one evidence-based user need.
2. Explain the difference between a feature, a benefit, and the value created for a user.
3. Compare ideas using usefulness, feasibility, user-need fit, and testability.
4. Write a simple value proposition and identify one key assumption to test.

# 4. From User Need to Possible Solutions

The User Need Card from Day 2 gives the team a clear direction, but it should not determine one specific solution.

A strong need statement leaves room for several possible responses. Day 3 therefore begins by expanding the number and variety of possible solutions before the team decides what to develop.

### Key Principle

**One need can have many possible solutions. Generate broadly before selecting carefully.**

## 4.1 Need, Solution, and Project Idea

| Element               | Meaning                                                                | Example                                                                                                     |
| --------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **User Need**         | The useful outcome the user is trying to achieve.                      | New students need a way to find complete and current club information.                                      |
| **Possible Solution** | One possible response to the need.                                     | A single club-information page, guided noticeboard, chatbot, or registration helper.                        |
| **Project Idea**      | A selected solution described clearly enough to explain and prototype. | A simple mobile-friendly club guide that helps new students compare options and confirm registration steps. |

## 4.2 A Good Need Statement Keeps the Solution Open

| Statement                                                           | Effect on Creativity                                                   |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| "Students need an app with notifications."                          | **Too narrow:** It has already selected a product and feature.         |
| "Students need a way to receive reliable deadline updates on time." | **Open:** Teams can explore several digital and non-digital solutions. |

---

# 5. Divergent and Convergent Thinking

Creative problem-solving uses two different modes of thinking.

**Divergent thinking** expands the range of possibilities.

**Convergent thinking** compares those possibilities and selects a direction.

Strong teams avoid mixing these two modes too early.

| Mode                    | Purpose                                                      | Helpful Behaviour                                                            | Common Risk                                                                      |
| ----------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Divergent Thinking**  | Create many different possibilities.                         | Say "Yes, and...", combine ideas, exaggerate, sketch, and postpone judgment. | Rejecting unusual ideas before their useful elements are explored.               |
| **Convergent Thinking** | Select the idea that best fits the evidence and constraints. | Use agreed criteria, explain decisions, and improve the selected idea.       | Choosing only the most exciting idea without checking usefulness or feasibility. |

## 5.1 Why Quantity Comes Before Quality

The first idea is often familiar, obvious, or influenced by the team's existing habits.

Generating several alternatives increases the chance of discovering a more useful direction.

**Quantity does not replace quality. It creates a stronger set of options for later evaluation.**

## 5.2 Rules for the Idea Generation Stage

* Focus on one named user and one user need.
* Generate ideas before evaluating them.
* Build on another person's idea instead of competing for ownership.
* Use words, quick sketches, diagrams, or short role-play to communicate ideas.
* Allow unusual ideas because a useful element may be hidden within them.
* Do not assume that every idea must use technology.
* Keep ideas safe, respectful, and appropriate for the camp environment.

### Useful Team Language

* "Yes, and..."
* "What if we...?"
* "We could combine..."
* "Another version might..."

# 6. Using Playful Constraints to Create Ideas

A creative constraint can make idea generation easier by giving the team a temporary rule or an unusual point of view.

The goal is not to keep every unusual idea. Instead, the goal is to break predictable thinking and discover useful elements that can later be adapted into realistic solutions.

## 6.1 Impossible Ideas

| Impossible Idea                                                 | Useful Element to Rescue                           | Possible Realistic Direction                                                     |
| --------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------- |
| A school bag that talks and completes every task.               | A reminder at the right moment.                    | A simple visual or audio reminder system for important tasks.                    |
| A robot that follows every student and turns off unused lights. | Automatic detection and timely action.             | A sensor concept or classroom exit checklist that signals when lights remain on. |
| A magic shield that blocks every dangerous link.                | Warning the user before opening or sharing a link. | A link-checking guide, browser warning concept, or awareness tool.               |
| A club guide that knows every student perfectly.                | Personalised suggestions based on interests.       | A short preference quiz that recommends suitable clubs.                          |

## 6.2 Idea Relay

In an **Idea Relay**, students build on one another's ideas through timed rounds.

The activity reduces ownership pressure and demonstrates that strong ideas can grow through collaboration.

Each contribution should make the idea:

* Clearer.
* More useful.
* Simpler.
* Easier to test.

### The Process

**1. Start**
Write or sketch one possible solution.

**2. Pass**
Give the idea to another student.

**3. Build**
Add a feature, user benefit, or simpler version.

**4. Combine**
Connect useful elements from different ideas.

**5. Review**
Identify the strongest possibilities.

# 7. Technical Lenses: Use Technology with Purpose

DECI students have experience across different technical areas.

A technical lens helps teams explore how their existing knowledge could support a user need. However, teams are not required to use every technical track.

Technology should support the value of the idea rather than become the value itself.

| Technical Lens       | Questions to Ask                                                                                   | Possible Contribution                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Web Development**  | Would a page, form, dashboard, or simple user flow make information or action easier?              | Landing page, information hub, booking flow, task dashboard, or paper interface.                             |
| **AI and Data**      | Would a recommendation, classification, pattern, or guided response help the user make a decision? | Recommendation flow, decision tree, chatbot storyboard, data-supported suggestion, or simulated AI response. |
| **Embedded Systems** | Would sensing, monitoring, alerting, or physical interaction help?                                 | Sensor concept, input-output diagram, device sketch, alert sequence, or automation storyboard.               |
| **Digital Art**      | Would stronger visual communication, identity, or storytelling improve the experience?             | Interface design, campaign concept, visual instructions, icons, animation storyboard, or project identity.   |
| **Cybersecurity**    | How can the idea protect information, access, privacy, and safe behaviour?                         | Safe login flow, privacy choices, warning messages, secure-use checklist, or risk-control diagram.           |

## 7.1 Technical Integration Levels

| Level                              | Description                                                                   | Example                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **No Technical Element**           | A service, process, or campaign may solve the need without a digital feature. | A clearer club-registration station with visual guidance.                 |
| **Technical Concept**              | The team explains how technology could support the idea without building it.  | A sensor diagram showing how an alert would be triggered.                 |
| **Simulated Technical Experience** | The team represents the behaviour using paper screens, cards, or role-play.   | One student acts as a chatbot while the user follows a conversation flow. |

### Scope Boundary

**Level 3 does not require programming, working hardware, live AI, real accounts, or a fully functional technical product.**

# 8. From Feature to Benefit to Value

Teams often describe an idea by listing its features.

A **feature** explains what the solution has or does.

A **benefit** explains how that feature helps the user.

**Value** explains why that benefit matters in the user's specific situation.

| Feature                                    | Benefit                                        | Value for the User                                                                          |
| ------------------------------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| One page containing all club details       | The student checks fewer sources.              | The student can make a decision with less confusion and a lower risk of missing a deadline. |
| A warning symbol beside an unfamiliar link | The student pauses before opening it.          | The student can make a safer decision before potential harm occurs.                         |
| A classroom light-status indicator         | The group can see that lights remain on.       | Students can reduce unnecessary energy use without relying on one person to remember.       |
| A colour-coded assignment view             | The student can quickly identify urgent tasks. | The student can prioritise work and reduce missed deadlines.                                |

## 8.1 Feature-Benefit-Value Questions

| Question                                                              | Purpose                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------- |
| **What does the idea do?**                                            | Identify the feature or main function.                        |
| **What becomes easier, faster, clearer, safer, or more enjoyable?**   | Identify the direct benefit.                                  |
| **Why does this benefit matter to the named user in this situation?** | Connect the benefit to the user need and supporting evidence. |

## 8.2 Avoid Feature Lists Without a User Connection

| Weak Description                                      | Stronger Value-Focused Description                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| "Our idea has notifications, colours, and a chatbot." | "Our idea gives students one clear place to confirm changed deadlines, helping them act before work becomes late." |
| "The device has a sensor and an alarm."               | "The sensor detects when a shared space is empty and reminds the last group to switch off unused lights."          |

# 9. Comparing Ideas: Would It Help?

After generating and improving several ideas, teams compare their strongest options.

The goal is not to prove that one student's idea is the best. The goal is to select the direction that creates the clearest value and can be explored through a simple prototype.

| Criterion                     | Guiding Question                                                                                  | Warning Sign                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Usefulness**                | Would the idea make a meaningful difference for the user?                                         | The idea is entertaining but does not improve the user's situation.                         |
| **User-Need Fit**             | Does the idea directly respond to the User Need Card?                                             | The idea solves a different problem or serves a different user.                             |
| **Feasibility**               | Can the team explain and represent the idea using the available time, skills, and materials?      | The idea depends on advanced systems, large budgets, or permissions the team does not have. |
| **Testability**               | Can a paper prototype, storyboard, role-play, or diagram help the team learn something important? | The idea is too broad to show a clear user journey or receive useful feedback.              |
| **Safety and Responsibility** | Is the idea respectful, safe, and appropriate?                                                    | It collects sensitive data, creates harm, or encourages unsafe behaviour.                   |

## 9.1 Simple Comparison Scale

| Score              | Meaning                                                                    |
| ------------------ | -------------------------------------------------------------------------- |
| **1 – Weak**       | The idea does not meet the criterion or requires major changes.            |
| **2 – Developing** | The idea partly meets the criterion, but important questions remain.       |
| **3 – Strong**     | The idea clearly meets the criterion and is ready for further development. |

## 9.2 Selection Is Followed by Improvement

The selected idea does not need to be perfect.

Teams may:

* Combine one useful element from another idea.
* Simplify an unrealistic feature.
* Change the technical approach.
* Reduce the scope.
* Clarify the user experience.

They then record the improved concept in the **Project Idea Card**.

# 10. Writing a Simple Value Proposition

A simple value proposition explains:

* Who the idea is for.
* What need it addresses.
* What the proposed solution is.
* What useful benefit it creates.

It should be clear enough for someone unfamiliar with the previous activities to understand the value of the idea.

### Value Proposition Template

**For [specific user] who needs [need], our idea is [solution] that helps them [main benefit].**

## 10.1 Building the Value Proposition

| Part         | Guiding Question                                | Example                                                                          |
| ------------ | ----------------------------------------------- | -------------------------------------------------------------------------------- |
| **User**     | Who experiences the selected need?              | New students interested in joining school clubs.                                 |
| **Need**     | What useful outcome are they trying to achieve? | Find complete and current club information before registration closes.           |
| **Solution** | What is the selected project idea?              | A mobile-friendly club guide with comparison cards and clear registration steps. |
| **Benefit**  | How will the user's experience improve?         | Students can compare options and take action without searching multiple sources. |

## 10.2 Strong and Weak Examples

| Value Proposition                                                                                                                                                                            | Evaluation                                                                                                                |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| "Our idea is a smart platform using AI and many features."                                                                                                                                   | **Weak:** The user, need, and benefit are unclear, and technology is being used as a label rather than a source of value. |
| "For new students who need reliable club information, our mobile-friendly guide brings current options and registration steps together so they can choose and register with less confusion." | **Strong:** It clearly identifies the user, need, solution, and benefit.                                                  |
| "We will make the best app for everyone."                                                                                                                                                    | **Weak:** The user is too broad and the claim is unsupported.                                                             |

---

# 11. Assumptions: What Must Be True?

Every new idea contains assumptions.

An **assumption** is something the team believes may be true but has not yet confirmed.

Identifying assumptions helps the team decide what the Day 4 prototype should explore.

| Assumption Type          | Guiding Question                                                           | Example                                                                |
| ------------------------ | -------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **User Assumption**      | Does the named user actually experience this need?                         | New students struggle to find current club information.                |
| **Value Assumption**     | Would the proposed benefit matter to the user?                             | Students would value comparing options in one place.                   |
| **Usability Assumption** | Would the user understand how to use the idea?                             | Students would understand the comparison cards and registration steps. |
| **Behaviour Assumption** | Would the user take the expected action?                                   | Students would check the guide before asking several people.           |
| **Technical Assumption** | Could the proposed technical behaviour work in a realistic future version? | The system could receive updated information from club leaders.        |

## 11.1 Main Assumption to Test

At Level 3, each team selects **one important assumption** that can be explored through a low-fidelity prototype.

The best assumption to test is usually related to whether:

* The user understands the idea.
* The user values the proposed benefit.
* The user can complete the intended user journey.

| Too Broad to Test                         | More Testable Assumption                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| "Our project will be successful."         | A new student can use the prototype to find one suitable club and identify the next registration step. |
| "AI will improve the experience."         | Users understand and trust the reason provided beside a simulated recommendation.                      |
| "The device will save energy everywhere." | Users notice the alert and understand the action the prototype asks them to take.                      |

### Day 4 Connection

**The prototype is built to learn about the main assumption, not to display every possible feature.**

# 12. Project Idea Card: Content Standard

The daily output is a **Project Idea Card** and **Simple Value Proposition**.

Together, they capture the team's decision and provide the foundation for the Day 4 prototype.

| Project Idea Card Field        | What the Team Records                                              | Quality Check                                                               |
| ------------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| **Project Idea Name**          | A short working name for the concept.                              | Is it clear and appropriate without making exaggerated claims?              |
| **Primary User**               | The specific user identified in the User Need Card.                | Does it match the Day 2 evidence?                                           |
| **User Need**                  | The useful outcome the team is addressing.                         | Is it written without prescribing the final solution?                       |
| **Selected Solution**          | A concise description of the proposed idea.                        | Can another person understand what the idea is?                             |
| **Main Feature or Experience** | The central action, flow, or interaction the team will represent.  | Is the scope small enough for a low-fidelity prototype?                     |
| **User Benefit**               | What becomes easier, clearer, safer, faster, or more useful.       | Is the benefit meaningful to the named user?                                |
| **Technical Connection**       | Optional DECI track contribution or simulated technical behaviour. | Does it support the value rather than distract from it?                     |
| **Reason for Selection**       | Why the team chose this idea using the comparison criteria.        | Does the explanation refer to usefulness, fit, feasibility, or testability? |
| **Simple Value Proposition**   | The user, need, solution, and main benefit in one clear statement. | Can someone understand the value without additional explanation?            |
| **Main Assumption to Test**    | One important belief that the prototype should explore.            | Can Day 4 testing produce useful evidence about it?                         |

## 12.1 Project Idea Quality Criteria

| Criterion         | Strong Evidence of Quality                                                      |
| ----------------- | ------------------------------------------------------------------------------- |
| **User-Centred**  | The idea responds to the named user and evidence-based need.                    |
| **Value-Focused** | The benefit is clear and meaningful rather than simply a list of features.      |
| **Focused**       | The team can represent the core experience without building a complete product. |
| **Feasible**      | The idea can be explored using paper, simple materials, diagrams, or role-play. |
| **Testable**      | The prototype can help the team learn about one important assumption.           |
| **Responsible**   | The idea respects privacy, safety, inclusion, and appropriate technology use.   |

# 13. Responsible and Inclusive Idea Design

Even a simple project concept should consider who might be excluded, what information may be collected, and whether the proposed behaviour could create harm or confusion.

At this stage, teams do not need to complete a full risk assessment. However, they should identify obvious concerns before selecting their final idea.

| Consideration                   | Questions for the Team                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Privacy**                     | Does the idea request personal information? Is all requested information necessary?                       |
| **Cyber Safety**                | Could the idea expose passwords, private accounts, unsafe links, or unauthorised access?                  |
| **Physical Safety**             | Does the idea involve electricity, tools, moving parts, or behaviour that should only be simulated?       |
| **Inclusion and Accessibility** | Could people with different abilities, language levels, or access conditions understand and use the idea? |
| **Bias and Fairness**           | Could recommendations or decisions treat some users unfairly?                                             |
| **Honest Claims**               | Are the team's claims realistic, or do they promise results that have not been tested?                    |
| **Environmental Impact**        | Could the idea reduce waste or energy use, or does it create unnecessary materials and devices?           |

# 15. Common Misconceptions and Corrections

| Misconception                                                  | Correction                                                                                                 |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| "The first idea is probably the best because it came quickly." | The first idea may be useful, but teams should generate alternatives before making a decision.             |
| "Unusual ideas waste time."                                    | Unusual ideas can reveal useful features, benefits, or new ways of thinking.                               |
| "A technical idea is automatically more valuable."             | Technology creates value only when it improves the user's experience or outcome.                           |
| "We need to use every DECI track in one project."              | Teams should use only the technical perspectives that strengthen the selected idea.                        |
| "More features make the project stronger."                     | A focused core experience is easier to explain, prototype, and test.                                       |
| "The feature and the benefit are the same thing."              | The feature describes what the idea does; the benefit describes how it helps the user.                     |
| "The highest total score always decides the idea."             | The scoring system supports discussion. Teams should also consider risks and important evidence.           |
| "The idea must be fully possible to build during the camp."    | The complete concept may be future-facing, but its core experience must be possible to represent and test. |
| "A value proposition is a slogan."                             | A value proposition clearly connects the user, need, solution, and benefit.                                |

---

# 16. Key Takeaways

* One user need can lead to many possible solutions.
* Divergent thinking creates options, while convergent thinking helps select and improve one direction.
* Teams should build on ideas before judging them.
* Technical knowledge is a lens for creating value, not a requirement to add complexity.
* A feature explains what the idea does; a benefit explains how it helps; value explains why it matters.
* Ideas should be compared using usefulness, user-need fit, feasibility, testability, and responsibility.
* A simple value proposition connects the specific user, need, selected solution, and main benefit.
* The Project Idea Card gives Day 4 a focused concept and one important assumption to test.

---

# 17. Reflection Questions

1. Which unusual idea helped our team discover a useful element?
2. Why did our selected idea fit the user need better than the other options?
3. Which assumption should our prototype help us explore tomorrow?
